# 任务拆解规则

## 拆解粒度

每个任务应是一个 Agent 可在一次调度中完成的工作单元：
- 预计实现时间：1-4 小时（人工估算等价）。
- 职责单一：一个任务只实现一个清晰的能力。
- 可验收：有明确的完成判断标准。

过大的任务应拆分；过小的任务应合并。

## Backend 任务拆解规则

### 必须独立成任务的

- 项目脚手架和基础配置（一个 BE 任务）。
- 数据库 schema / migration（每组关联表一个任务）。
- 每个独立的 API 端点或端点组（CRUD 为一组）。
- 外部系统集成（每个外部系统一个任务）。
- 定时任务 / 后台 job。
- 认证和授权模块。

### 拆解示例

```
BE-01: 项目脚手架搭建（Spring Boot / Express / ...）
BE-02: 数据库表结构和 ORM 实体
BE-03: 用户认证 API（注册、登录、token 刷新）
BE-04: 订单 CRUD API
BE-05: 支付集成（调用第三方支付）
BE-06: 消息通知服务
```

## Frontend 任务拆解规则

### 必须独立成任务的

- 项目脚手架和基础配置（路由、状态管理、HTTP 客户端）。
- 每个页面或页面组（紧密关联的列表+详情可合并）。
- 公共组件库（如果需要多页复用）。
- 全局状态管理。

### 拆解示例

```
FE-01: 前端脚手架搭建（React / Vue / ...）
FE-02: 登录页和认证流程
FE-03: 订单列表页 + 详情页
FE-04: 订单创建表单
FE-05: 数据导出功能
```

## Test 任务拆解规则

### 按测试层次

- `unit`：纯逻辑单元测试（工具函数、业务规则计算）。
- `integration`：API 集成测试（后端 API + 数据库）。
- `e2e`：端到端测试（前后端联调验证）。

### 拆解示例

```
TEST-01: 认证模块单元测试
TEST-02: 订单 API 集成测试
TEST-03: 核心业务流程 E2E 测试
```

## 依赖规则

1. Frontend 消费 API 的任务必须依赖提供该 API 的 Backend 任务。
2. Test 任务依赖其覆盖的所有 coding 任务。
3. 同类型任务间的依赖只有在存在数据层面的先后关系时才标注。
4. 不允许循环依赖。

## 验收标准来源

任务的 acceptance_criteria 从以下来源推导：
- 需求的验收标准（Given/When/Then）→ 对应到实现该需求的任务。
- 方案的接口设计 → 对应到 API 实现任务。
- 方案的数据模型 → 对应到数据库和 CRUD 任务。
- 原型的交互流程 → 对应到前端页面任务。

## 复杂度评估

| 级别 | 标准 |
|------|------|
| low | 少量文件（1-3），模式化实现，无复杂逻辑 |
| medium | 适量文件（3-6），有业务逻辑，可能需要外部调用 |
| high | 多文件（6+），复杂逻辑，多外部依赖，并发/事务处理 |
